# Lesson 5: 記事の実験を理解する

## ゴール

[「ぱけっとぽいぽい」](https://qiita.com/Suisan-neki/items/cafab8fd958a80ab10ee)を自分の言葉で説明できる。

Lesson 0〜4 で、パケットが NIC からアプリに届くまでの流れ（NIC → ドライバ → XDP → sk_buff → Netfilter → ソケットバッファ → ユーザー空間）と、「どこで見えて、どこで見えなくなるか」を手で確認してきた。この記事は、その流れの「どこで捨てるか」を実際に測った実験になっている。

## 記事の内容

Rust と Raspberry Pi 2台で、同じ不要な UDP 通信（ポート4000、128bytes）を「どこで捨てるか」によって受信側の負荷がどう変わるかを実測した実験。

### 実験設計

- Pi A が UDP 負荷と HTTP リクエスト（約200ms間隔）を送り、Pi B が受信・計測する
- 比較した破棄位置は3つ
  - XDP で `XDP_DROP`
  - nftables の `input` hook で `drop`（= Lesson 4 でやったこと）
  - UDP ソケットまで届けて `recv_from()` した後に読み捨て（= Lesson 3 でやったことに近い）
- 実装はRust、eBPFには Aya を使用
- 測定順をローテーションし、pps を昇順/降順で交互に測って偏りを減らす
- 送信側の限界が混ざらないよう、actual pps が目標の90%未満なら「測定不成立」にする
- 片付けは `SIGINT` の処理と `Drop` trait で行う

### 結果（50,000 pps、CPU使用率の中央値）

- XDP: 5.3%
- nftables: 6.7%
- ユーザー空間: 9.8%

XDPとnftablesの差は小さく、nftablesとユーザー空間の差の方が大きく出た。HTTP成功率は全条件で100%、p95も1〜2msで、サービス維持の限界には到達していない（100,000 ppsでも同様。この時点でPi Aの送信能力が先に限界に近づいている）。

### 著者の学び

- クラウドが隠している処理を自分で組むと、パケットがアプリに届くまでの理解が深まる
- リソースの乏しいエッジ環境では数ポイントの差も無視できない
- 「できるだけ早く捨てる」が正解なのではなく、判断に必要な情報が揃った段階で捨てるという責務分離が大事

## 前提知識の棚卸しポイント

- **XDPのGenericとNativeの違い**: Nativeは NICドライバの受信経路で動き、`sk_buff`（カーネルのパケット構造体）の生成前に捨てられる。Genericはその後で動くので、早期破棄の利点がかなり薄れる。記事の「XDPとnftablesの差が小さい」結果は、これで説明できる可能性が高い
- **Netfilterのhookの位置**: `prerouting → input / forward → output → postrouting`（Lesson 4で実際に使った）
- **eBPF verifier**: 境界チェックが必須なのは、検証器が範囲外アクセスの可能性があるプログラムを拒否するため（Lesson 3の長さチェックと同じ発想）

## セキュリティ面の突っ込み（記事への指摘）

- IPv4オプション付きパケットでXDPのフィルタを回避できる。IHLが5以外なら `XDP_PASS` する実装なので、攻撃者がIPオプションを付けるだけで素通りする。IPv4フラグメント、VLANタグ付きフレーム、IPv6も同様に素通り。実験用と明記されているので許容範囲だが、「防御」として使うなら致命的。パーサを限定したときは、限定範囲外を PASS するのか DROP するのか（fail-open か fail-closed か）を意識して設計する必要がある
- 境界チェック失敗時に `XDP_ABORTED` を返している。実質ドロップになるが、正常な通信を巻き込むリスクがある
- `NftGuard` の `Drop` で `let _ =` を使ってエラーを握りつぶしている。後片付けに失敗してもルールが残ったまま気づけない。ログは出すべき。また、`SIGKILL` や電源断では `Drop` も `SIGINT` ハンドラも走らないので、起動時に残骸を掃除する処理も必要（Lesson 4のセキュリティ注意と同じ）
- XDPのロードには特権（root や `CAP_BPF`）が必要。実験LANは外部と分離されていて良い判断だが、本番に持ち込むならローダーの権限管理や攻撃面を考える必要がある
- `/api/ping` が認証なしの8080番で公開されている。実験用途なら問題ないが、展示会場のネットワークにつないだ瞬間にリスクになる

## 実験の品質への突っ込み

- n=3 で中央値を取っているだけなので、統計的な主張は弱い（例: XDPの7.2 / 5.0 / 5.3%のようにばらつきが大きく、XDPとnftablesの1.4ポイント差が有意かは判断できない）
- 測っているのは全コア合算のCPU使用率だけ。受信処理は特定コアの softirq に偏りやすいので、コア別使用率や `/proc/softirqs`（NET_RX）の分布を見ないと、実際のボトルネックは分からない
- HTTPに影響が出なかったのは負荷が足りなかったから。「差が出なかった」というより「差が出る領域に到達できなかった」と捉えるのが正確（記事もそう書いている）

## 自分の言葉で説明してみる

- パケットがNICに到着してからUDPソケットの `recv_from()` に届くまでの流れ（NIC → ドライバ → XDP → sk_buff → Netfilter → ソケットバッファ → ユーザー空間）
- XDPの Generic と Native の違いが、なぜ「XDPとnftablesの差が小さい」結果につながるのか
- 3つの破棄位置（XDP / nftables / ユーザー空間）のうち、自分がLesson 1〜4でどこまで再現できたか
